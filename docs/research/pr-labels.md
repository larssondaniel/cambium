# Per-PR acknowledgement label: GitHub mechanics (research)

Researched 2026-10-24. Sources are primary only: docs.github.com, github.blog changelog, GitHub's OpenAPI description (github/rest-api-description, `main` at `755ee33`), GitHub-maintained webhook payload examples (octokit/webhooks), the source of the actions and bots cited, and live `gh api` responses. Each claim has its source next to it. Anything not confirmed by a primary source is marked **UNVERIFIED**.

## TL;DR

1. `pull_request` runs only on `opened`, `synchronize` and `reopened` by default. To react to a label being added or removed, the workflow must list `labeled` and `unlabeled` under `types:`. Listing `types:` replaces the default set, so the snippet has to name all five.
2. Every `pull_request` payload carries `pull_request.labels[]`, including `synchronize`. The schema marks it required, with `id`, `node_id`, `url`, `name`, `color`, `default` and `description`, plus `archived_at` and `archived_by` on newer schemas. A `labeled` or `unlabeled` payload also has a top-level `label` object. `@actions/github` `context.payload` is the raw event JSON from `GITHUB_EVENT_PATH`, so `context.payload.pull_request.labels` needs no API call.
3. Applying or removing a label needs **Triage** or higher. Creating, editing or deleting a label needs **Write** or higher. A PR author with only Read access cannot label their own PR. Outside collaborators get no base permissions, and org members default to Read on public repos, so both need an explicit Triage grant.
4. A maintainer can label fork and Dependabot PRs. The resulting `pull_request` `labeled` run still treats the PR as a fork: the token is read-only and no secrets are passed. Reading labels from the payload needs no write scope, so it works there.
5. Each workflow run creates its own check suite. When a `labeled` run passes after a `synchronize` run failed on the same head SHA, **both** check runs stay on the commit (seen live via `gh api`). The docs say only that required checks "must pass on the latest commit SHA". Which same-named check run branch protection uses is **not documented** (**UNVERIFIED** that the newest one wins).
6. A re-run uses "the same `GITHUB_SHA` … and `GITHUB_REF`" as the original event. Whether the payload is also the original is not documented. amannn/action-semantic-pull-request's source comment says the context PR data is stale on re-run. So with payload-only reading, the **Re-run** button probably will not see a label added later. Only a new `labeled` run will. GraphQL Inspector avoids this by fetching the PR via the API.
7. In the REST API, adding labels needs Issues **or** Pull requests write, and so does creating a label. The docs do not say whether "Add labels to an issue" auto-creates a missing label (**UNVERIFIED**). Archived labels "cannot be added to issues or pull requests" (OpenAPI, 2026).
8. Prior art: GraphQL Inspector's `approve-label` (default `approved-breaking-change`) forces the check to SUCCESS and the title reads "Everything looks good". It never tells the reader the label exists, which is exactly what open issue #2656 (2023) asks for. changelog-enforcer (`Skip-Changelog`) and action-semantic-pull-request (`ignoreLabels`, no default) also leave discovery to the docs. Prow's release-note plugin is the counter-example: its bot comment names the label.
9. No documented length or character limits on label names were found. The API looks names up case-insensitively (live probe), but payloads carry the stored case, and every action surveyed matches with exact, case-sensitive `===` or `includes`. changelog-enforcer's own repo shows the trap: the default input is `Skip-Changelog`, the repo label is `skip-changelog`, and its own workflow has to override the input.
10. 2025-2026 changes worth knowing: label archiving and repo-usage label suggestions went GA on 2026-08-27. Agent "suggest, don't apply" controls are in preview for Issues only, and the Add-labels endpoint now has `suggest`, `rationale` and `confidence` fields. Issue types and sub-issues apply to issues, not PR labels. Nothing changes how `labeled` events or payload labels work.

## 1. `pull_request` activity types and the `labeled` payload

- The activity types are `assigned`, `unassigned`, `labeled`, `unlabeled`, `opened`, `edited`, `closed`, `reopened`, `synchronize`, `converted_to_draft`, `locked`, `unlocked`, `enqueued`, `dequeued`, `milestoned`, `demilestoned`, `ready_for_review`, `review_requested`, `review_request_removed`, `auto_merge_enabled` and `auto_merge_disabled`. https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request
- Default set: "By default, a workflow only runs when a `pull_request` event's activity type is `opened`, `synchronize`, or `reopened`." (same page)
- `labeled` and `unlabeled` are not in the default set, so they must be listed explicitly. changelog-enforcer's README shows the pattern: `types: [opened, synchronize, reopened, ready_for_review, labeled, unlabeled]`, with the note "(which are not included by default for the "pull_request" trigger)". https://github.com/dangoslen/changelog-enforcer#usage . action-semantic-pull-request says the same in its `ignoreLabels` input description. https://github.com/amannn/action-semantic-pull-request/blob/main/action.yml
- **`labeled` payload.** "A label was added to a pull request." It has `label` (object, not marked required), `number` (required) and `pull_request` (required). https://docs.github.com/en/webhooks/webhook-events-and-payloads#pull_request . In the OpenAPI schema `webhook-pull-request-labeled`, `required` is `[action, number, pull_request, repository, sender]` and `label` is a `$ref` to `webhooks_label`. https://github.com/github/rest-api-description (descriptions/api.github.com/api.github.com.json)
- **Does `pull_request.labels[]` already include the new label?** Yes in GitHub's example: in `labeled.payload.json`, the top-level `label` (`bug`) also appears in `pull_request.labels`. https://github.com/octokit/webhooks/blob/main/payload-examples/api.github.com/pull_request/labeled.payload.json . The docs do not state it in prose, so it is **UNVERIFIED** as a guarantee. Caveat: the same repo's `unlabeled.payload.json` *still lists* the removed `bug` label in `pull_request.labels`. https://github.com/octokit/webhooks/blob/main/payload-examples/api.github.com/pull_request/unlabeled.payload.json . The examples may be hand-made or stale, so whether `unlabeled` payloads reflect the removal is **UNVERIFIED**. A defensive reader could subtract `label.name` when `action === 'unlabeled'`.

## 2. `pull_request.labels[]` shape and availability

- OpenAPI `webhook-pull-request-*` schemas (`opened`, `reopened`, `synchronize`, `edited`, `labeled`, `unlabeled`, all checked) include `labels` in `pull_request.required`. Items are `{id, node_id, url, name, color, default, description}`, all required. `description` is nullable and `color` is a "6-character hex code, without the leading #". The `labeled` schema (and `webhooks_label`) also adds `archived_at` and `archived_by`, both nullable. https://github.com/github/rest-api-description
- The `synchronize` payload includes `pull_request` (required) plus `before` and `after`. https://docs.github.com/en/webhooks/webhook-events-and-payloads#pull_request . octokit's `synchronize.payload.json` carries `pull_request.labels`. https://github.com/octokit/webhooks/blob/main/payload-examples/api.github.com/pull_request/synchronize.payload.json
- Live REST shape (`GET /repos/dangoslen/changelog-enforcer/pulls/307`): `{"color":"e8a35a","default":false,"description":"","id":2016785371,"name":"skip-changelog"}`. Here `description` is an empty string, not null.
- **Actions `github` context.** `github.event` is "The full event webhook payload", and it "is identical to the webhook payload of the event that triggered the workflow run". https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context . So `github.event.pull_request.labels.*.name` works in expressions.
- **`@actions/github`.** The `Context` constructor does `this.payload = JSON.parse(readFileSync(process.env.GITHUB_EVENT_PATH))`, so `context.payload.pull_request.labels` is the raw webhook array. https://github.com/actions/toolkit/blob/main/packages/github/src/context.ts

## 3. Who can add or remove a label

- Repository roles table: **Apply/dismiss labels** is allowed for Triage, Write, Maintain and Admin, and not for Read. **Create, edit, delete labels** is allowed for Write, Maintain and Admin, and not for Read or Triage. https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization
- "Anyone with triage access to a repository can apply and dismiss labels." "Anyone with write access to a repository can create a label." Edit and delete also need write, and deleting a label removes it from every issue and PR. https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/managing-labels
- Labels are per repository: "You can apply labels in the repository the label was created in." (same page)
- **PR author without triage.** The table gives Read no "apply/dismiss labels" right, and no docs page makes an author exception. So an outside contributor cannot self-apply the label. That follows from the table; no page states the author case outright.
- **Org members.** "By default, members of an organization will have **Read** permissions to the organization's public repositories." Base permission is configurable, and if it is Read, members also cannot label. https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/setting-base-permissions-for-an-organization
- **Outside collaborators.** "Base permissions do not apply to outside collaborators." They need an explicit role of Triage or higher. (same page)
- **Bots.** `pull-requests: write` is described as allowing a workflow to "add a label to a pull request". https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions . But "events triggered by the `GITHUB_TOKEN` will not create a new workflow run" (except `workflow_dispatch` and `repository_dispatch`). A label added by another workflow using `GITHUB_TOKEN` will **not** trigger the `labeled` run. https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow

## 4. Fork and Dependabot PRs

- Anyone with Triage or higher can label any PR in the repo, including fork PRs, because labels are a base-repo object (section 3). Nothing in the docs restricts labelling by PR origin.
- "The `GITHUB_TOKEN` has read-only permissions in pull requests from forked repositories." https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflows-in-forked-repositories . This is stated for the `pull_request` event as a whole, not per activity type. So a `labeled` run on a fork PR is still downgraded. No docs sentence names `labeled` specifically, so that point is **UNVERIFIED**, but the downgrade is event-wide. See also `pr-comment-permissions.md` §3.
- Fork-run approval: fork PR runs "may require manual approval from a maintainer with write access". https://docs.github.com/en/actions/how-tos/manage-workflow-runs/approve-runs-from-forks . Whether a `labeled` run started by a maintainer's action also waits for approval is not stated (**UNVERIFIED**).
- Dependabot: "Workflows triggered by Dependabot pull requests are treated as though they are from a forked repository". https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows . They "receive a read-only `GITHUB_TOKEN` and do not have access to any secrets", and "a re-run of a Dependabot workflow keeps its original privileges". https://docs.github.com/en/code-security/dependabot/troubleshooting-dependabot/troubleshooting-dependabot-on-github-actions . Whether a human labelling a Dependabot PR produces a Dependabot-restricted run or an ordinary one is **UNVERIFIED**. The current docs no longer say how a run is classified as Dependabot-triggered.
- **Conclusion.** Labels come in the payload (section 2), so reading them needs no token scope and no API call. It works on fork, Dependabot and same-repo PRs alike.

## 5. Required status checks when a label triggers a new run

- "Required checks must pass on the latest commit SHA. Checks from earlier commits don't satisfy the requirement." "If a check and a commit status have the same name, both must pass when that name is required." https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks
- "Required status checks must have a `successful`, `skipped`, or `neutral` status". Also, "Using the same job name in multiple workflows can cause ambiguous status check results" and "make sure that job names are unique across all workflows". https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches
- Rulesets: "all required status checks must pass". The section does not say which run wins either. https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets
- Checks API: "A check suite is a collection of the check runs created by a single GitHub App for a specific commit." https://docs.github.com/en/rest/guides/using-the-rest-api-to-interact-with-checks . The `filter` param on "List check runs for a Git reference" says "`latest` returns the most recent check runs" and is the default. https://docs.github.com/en/rest/checks/runs
- **Live observation** on `dangoslen/changelog-enforcer` PR #307, head `2bb9464…`, which was labelled `skip-changelog` and merged 2026-04-27. Three `github-actions` check suites sit on one SHA. `enforce-changelog` has check runs `skipped`, then `failure` (00:21:13), then `success` (00:21:46). `filter=latest` and `filter=all` return the same nine runs, so "latest" is per suite and the old failure stays visible on the commit. Commands: `gh api repos/dangoslen/changelog-enforcer/commits/2bb946482b2333b451b9c17693f8cdd39336b2f4/check-runs?filter=all` and `.../check-suites`. That repo has no required contexts (`required_status_checks.contexts: []`), so this does not show how merge gating behaves.
- **UNVERIFIED:** that branch protection evaluates only the most recent check run per name, so the newer `success` from the `labeled` run unblocks the merge. No docs page states this. Commit statuses document "the latest status for all contexts". https://docs.github.com/en/rest/commits/statuses . There is no matching sentence for check runs.
- Re-runs: "Re-runs use the privileges of the actor who initially triggered the workflow", and the run uses "the same `GITHUB_SHA` … and `GITHUB_REF` … of the original event". https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs . The page says nothing about the payload. action-semantic-pull-request's source: "The pull request info on the context isn't up to date. When the user updates the title and re-runs the workflow, it would be outdated. Therefore fetch the pull request via the REST API". https://github.com/amannn/action-semantic-pull-request/blob/main/src/index.js . Primary docs do not confirm that re-runs replay the original payload (**UNVERIFIED**), but the tool's author designed around it.

## 6. REST: adding and creating labels

- `POST /repos/{owner}/{repo}/issues/{issue_number}/labels` "Adds labels to an issue." The body is `{"labels": [...]}` with `minItems: 1`, and items are strings or `{name, rationale, suggest, confidence}`. `suggest: true` means "the label is stored as a pending suggestion for human review rather than applied directly." Responses are 200, 301, 404, 410 and 422. https://docs.github.com/en/rest/issues/labels#add-labels-to-an-issue and the OpenAPI.
- **Auto-create of missing labels:** neither the docs nor the OpenAPI say. **UNVERIFIED** either way. It was not tested, because that would mean writing to a repo.
- `POST /repos/{owner}/{repo}/labels` "Creates a label … The name and color parameters are required." In the OpenAPI schema only `name` is `required`. `name` allows emoji ("native emoji or colon-style markup"). `color` is hex without `#`, and `description` "Must be 100 characters or fewer." (same sources)
- `PATCH /repos/{owner}/{repo}/labels/{name}` takes `archived`. "Archived labels cannot be added to issues or pull requests." (OpenAPI)
- **Permissions** ("Permissions required for GitHub Apps"): POST and PUT `issues/{n}/labels`, DELETE `issues/{n}/labels/{name}`, POST `labels` and PATCH `labels/{name}` all need **write**, listed under both Issues and Pull requests with the "Additional permissions" mark (one of the set is enough). GET `issues/{n}/labels` needs read. https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps
- For the person behind a token, label create, edit and delete need the Write role and apply needs the Triage role (section 3).

## 7. Prior art

### GraphQL Inspector action (graphql-hive/graphql-inspector, `run.ts` last changed in `e9db2c4`, 2026-09-29)

- Input: `approve-label`, described as "Label to mark Pull Request introducing breaking changes as safe and expected ("approved-breaking-change" by default)". https://github.com/graphql-hive/graphql-inspector/blob/master/action.yml
- Code: `const approveLabel = core.getInput('approve-label') || 'approved-breaking-change';` https://github.com/graphql-hive/graphql-inspector/blob/master/packages/action/src/run.ts
- **How it reads labels: through the API, not the payload.** `getAssociatedPullRequest` calls `GET /repos/{owner}/{repo}/commits/{commit_sha}/pulls` and takes `result.data[0]`. The SHA comes from `git rev-parse HEAD`, or the PR head parsed out of a "Merge X into Y" commit message. https://github.com/graphql-hive/graphql-inspector/blob/master/packages/action/src/git.ts . This makes it event-agnostic: it works on `push`, and a re-run sees fresh labels.
- **Matching:** `pullRequest?.labels?.some(label => label.name === approveLabel)`, which is exact and case-sensitive. (run.ts)
- **What happens when the label is present:** if `(failOnBreaking === false || hasApprovedBreakingChangeLabel) && conclusion === Failure`, it logs `'FailOnBreaking disabled. Forcing SUCCESS'` and sets `conclusion = Success`. The check-run title then becomes `'Everything looks good'`. The summary (`createSummary(changes, …)`) and annotations still list the breaking changes. The step does not fail. It does not say that a label caused the pass. Its log line even attributes it to `fail-on-breaking`. (run.ts)
- Docs: "To mark the breaking change as safe, apply the `approved-breaking-change` label or define your own in `approve-label`." The quick-start example uses `on: [push]` and does not mention `labeled` triggers. https://github.com/graphql-hive/graphql-inspector/blob/master/website/content/docs/products/action.mdx
- **Issue #2656**, "Suggest PR Label to Bypass Breaking Change Check" (open, 2023-11-08, by maxmelamed). The requester says the inspector "does not make clear what the correct label to use is". They want "the breaking change message to include a suggestion of what label to use in case the breaking change is expected". They rejected a workaround (a separate workflow step that comments the label on failure) as less clean. A maintainer (Urigo) welcomed a PR and asked whether the docs should improve too. PR #2887 (opened 2025-05-08, still open) takes a broader route: configurable success and failure messages. https://github.com/graphql-hive/graphql-inspector/issues/2656 , https://github.com/graphql-hive/graphql-inspector/pull/2887

## 8. Label names

- No documented length limit or character set was found in the REST docs, the OpenAPI or the "Managing labels" page. The only documented constraints are that emoji are allowed in `name` and that `description` is at most 100 characters. https://docs.github.com/en/rest/issues/labels . A UI cap on name length (often cited as 50) is **UNVERIFIED**.
- changelog-enforcer asserts "GitHub labels do not allow for leading or trailing spaces". This is a third-party claim (**UNVERIFIED** in GitHub docs).
- **Case.** Live probe: `GET /repos/dangoslen/changelog-enforcer/labels/{Skip-Changelog|skip-changelog|SKIP-CHANGELOG}` all return id `2016785371` with `name: "skip-changelog"`. Search `label:Skip-Changelog` and `label:skip-changelog` both return 73. So API lookup and search are case-insensitive. Payloads carry the stored case. That two labels differing only in case cannot coexist is **UNVERIFIED** (not tested, as it needs a write).
- Matching in tools is whatever the tool does. All three Actions above use exact string equality on `label.name`.
- Conventions: Kubernetes uses slash-namespaced, lowercase, hyphenated names (`kind/bug`, `area/…`, `sig/…`, `do-not-merge/hold`, `tide/merge-method-squash`), plus flat names such as `lgtm`, `approved`, `release-note-none`. https://github.com/kubernetes/test-infra/blob/master/label_sync/labels.md . GitHub's defaults are lowercase, some with spaces (`good first issue`, `help wanted`, `wontfix`). https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/managing-labels . Colon-separated styles (`type: bug`) exist in the wild, but no primary source was gathered for them.

## 9. Other events

- `issue_comment`: the payload has `issue` (with `issue.labels`) and `issue.pull_request` holding only `{url, html_url, diff_url, patch_url, merged_at}`. There is **no** top-level `pull_request`, so `context.payload.pull_request` is undefined. (OpenAPI `webhook-issue-comment-created`). The docs suggest `github.event.issue.pull_request` to detect PR comments. https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issue_comment
- `workflow_dispatch`: the payload properties are `enterprise`, `inputs`, `installation`, `organization`, `ref`, `repository`, `sender` and `workflow`. There is no PR and no labels. (OpenAPI `webhook-workflow-dispatch`)
- For Cambium, which runs only on `pull_request`, payload labels are always present (section 2). Nothing else is needed unless a future feature supports other events, in which case GraphQL Inspector's commit-to-PR API lookup is the known pattern.

## 10. 2025-2026 changelog items touching labels

- **2026-08-27, label archiving GA and label suggestions.** You can "archive labels you no longer use without losing their history on existing issues". You "can unarchive a label at any time". Suggestions are "based on what a repository has been using recently", and "Recent labels" are per user. No API or webhook changes are announced. https://github.blog/changelog/2026-08-27-label-archiving-is-generally-available/ . The OpenAPI adds `archived_at`/`archived_by` to label objects (webhook schemas included) and says "Archived labels cannot be added to issues or pull requests."
- **2026-07-23, agent automation controls (Issues, public preview).** Agents can suggest instead of apply, for labels, fields, type, close and assignees. Suggestions "wait in a panel on the issue instead of taking effect". Approvals are "a workflow convenience, not a security control". PRs are not mentioned. https://github.blog/changelog/2026-07-23-agent-automation-controls-in-github-issues-in-public-preview/ . This matches the new `suggest`/`rationale`/`confidence` fields on Add labels (section 6). A *suggested* label is presumably absent from `labels[]` until accepted (**UNVERIFIED**).
- **2026-04-09, "Repository member role labels" in the PR list.** These are author-association badges (`First-time contributor`, `Member`), not repository labels. https://github.blog/changelog/2026-04-09-repository-member-role-labels-now-in-pull-request-list-view/
- **2025-04-09, sub-issues and issue types GA.** These are issue-only concepts and do not change PR labels. https://github.blog/changelog/2025-04-09-evolving-github-issues-and-projects/
- **2025-05-22**, deprecation of bulk issue-to-discussion conversion via labels. Not relevant to PRs. https://github.blog/changelog/2025-05-22-deprecation-of-bulk-conversion-of-issues-to-discussions-via-labels/
- No 2025-2026 changelog entry was found that changes `pull_request` `labeled`/`unlabeled` semantics or label payloads beyond the archive fields.

## Implications for Cambium (inference, not sourced)

- Read labels from `context.payload.pull_request.labels`. This needs no API call and no extra permission, and it works on forks and Dependabot. The cost: a Re-run after labelling probably will not see the label, so the comment should say a new run starts automatically once the label is added, provided the workflow lists `labeled`/`unlabeled`.
- The README snippet must list `types: [opened, synchronize, reopened, labeled, unlabeled]`. Otherwise adding the label does nothing until the next push. This is the most likely support question.
- Consider a guard: if a breaking change is found and the label input is set, but `labeled` was never seen, Cambium cannot tell that from the payload. Docs and the comment text are the real defence.
- Name the label in the sticky comment and the job summary. This is the gap GraphQL Inspector #2656 has left open since 2023, and the main differentiator against all surveyed Actions.
- When the label lets a change through, say so explicitly ("accepted via label `schema-change-accepted`"). Do not report it as "Everything looks good" like Inspector does. The breaking changes should stay listed.
- Match case-insensitively and trimmed, so `Schema-Change-Accepted` versus `schema-change-accepted` does not silently fail. GitHub itself treats names case-insensitively in lookup and search.
- Do not create the label. That would need `issues`/`pull-requests: write` and the Write role, the auto-create behaviour of Add-labels is unverified, and the token is read-only on forks anyway. Document a one-line `gh label create` instead.
- Triage is enough to apply the label, which is less than merge rights. That is fine for an acknowledgement, but the docs should say the label is not a review approval. If teams want it gated harder, they can rely on CODEOWNERS or required reviews.
- With `unlabeled`, the next run fails again. That is the correct behaviour, and it depends on the unverified "newest check run wins" rule for branch protection. Recommend a single job name (no separate label workflow) to avoid the documented duplicate-name ambiguity.
- An archived label cannot be newly applied. If the configured label is archived, users will be confused. That is a candidate troubleshooting note, not a code path.
